# Internationalization (i18n)

Retrofitting i18n is one of the most expensive refactors there is — it touches every screen, every
email, every error message. Deciding early costs almost nothing; deciding late costs a quarter.

## The decision to make now

Even if you ship one language today: **are strings hardcoded, or do they go through a lookup?** The
cost difference between the two is small on day one and enormous on the day someone asks for a second
locale. If a second locale is plausible within two years, start with the lookup.

## The rules that avoid the expensive mistakes

1. **No concatenation.** `"You have " + n + " items"` cannot be translated — word order and
   pluralization differ per language. Use interpolation with named parameters:
   `t('cart.items', { count: n })`.
2. **Pluralization is a library feature.** English has 2 forms; Arabic has 6; Polish has 4 with
   non-obvious rules. Never write `count === 1 ? 'item' : 'items'` by hand.
3. **Never translate a key.** `t('save')` is fine; building the key from a variable
   (`t('button.' + action)`) makes every key invisible to static analysis and to the extraction tool.
4. **Dates, numbers and currency go through `Intl`**, never hand-formatted. `1,000.50` and `1.000,50`
   are the same number in different locales, and getting it wrong in a financial UI is a support
   ticket.
5. **Give translators context.** A key named `common.submit` with no comment gets translated wrongly
   in half the languages, because "submit" is a verb in one context and a noun in another.

## What people forget

- **Emails and notifications** — usually built outside the UI's i18n system, and therefore always in
  one language.
- **Error messages from the back end.** Either the API returns a **code** the front end translates
  (preferred), or the API needs to know the user's locale. Returning a hardcoded English string is
  the choice that costs later.
- **Validation messages**, which usually come from a schema library's defaults.
- **PDFs, exports and reports.**
- **`document.title`, meta tags, and the `lang` attribute** — which is also an accessibility
  requirement, since a screen reader uses it to choose a voice.

## Layout consequences

- **Text expands.** German is routinely 30% longer than English. A button sized to fit its English
  label will break.
- **RTL** (Arabic, Hebrew) mirrors the entire layout. Using logical CSS properties
  (`margin-inline-start` rather than `margin-left`) makes this nearly free — using the physical ones
  makes it a rewrite.
- Never bake text into an image.

## Checklist for new UI

- [ ] No user-visible string hardcoded in a component.
- [ ] Interpolation with named parameters; no concatenation.
- [ ] Plurals through the library's plural rules.
- [ ] Dates/numbers/currency through `Intl`.
- [ ] The layout survives a 30% longer string.
- [ ] `lang` set correctly (a11y and i18n at once).
