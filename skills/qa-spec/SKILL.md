# qa-spec — a scenario becomes a test that proves something

Automating is not "writing a test that passes": it is turning repeated manual work into a proof that
runs by itself and **fails when the behavior breaks**. A green test that never fails is maintenance
cost pretending to be a safety net.

Source of the scenario: the catalog (`qa/references/scenario-catalog.md`). Write back to it.

> **Actually running it?** Follow the playbook step by step, with a gate and an observable output at
> each stage: `references/automate-scenario.md`. This skill holds the judgment (which level, what the
> assertion proves); the playbook holds the sequence.

## Step 1 — Input: a catalog id, or loose text that becomes an entry

- **Id (`checkout-014`)**: read the entry in `scenarios/*.yaml`. It is the source — do not
  reinterpret the `when`/`then`.
- **Loose text**: **structure it first** (given/when/then, criticality, journey), **show it and
  confirm**, and only then generate. A badly worded scenario generates a test that proves something
  else — and nobody finds out, because it passes.

Once confirmed, the entry goes into the catalog (`status: draft`, `origin:`) **before** the code:
without an entry the test is born an orphan, and `preflight` flags it (catalog ↔ spec).

## Step 2 — Target level: argue for going down

The scenario says `target_level`, but it is **a proposal, not an order**. If the behavior fits below
L3, **say so and propose going down**, with one sentence saying why. Going down is the compound gain
of the design: faster, more stable, runs on every PR. Going up without need is how an e2e suite gets
slow and flaky.

| Level | What it is | When it is right |
|---|---|---|
| **L0 · unit** | an isolated unit, no I/O | the rule is a calculation or a domain decision |
| **L1 · integration** | unit + a real nearby dependency (database, service in a container) | the risk is in talking to the infrastructure |
| **L2 · contract** | the agreement between two sides (OpenAPI/Pact/Avro) | the risk is the other repo changing under you |
| **L3 · E2E** | the system end to end (full API or browser) | the risk only shows up with everything together |
| **L4 · exploratory** | a person with heuristics, no script | it depends on human judgment — **not automated** |

Detail, examples and the question that decides each rung: `test-strategy/references/test-levels.md`.

## Step 3 — LOCK: no factory, no test

Before writing a line, check that **every trait in `given:`** exists in the repo's factories
(`test-data`). If any is missing:

> **Stop. Do not generate the test.** Say exactly which trait is missing, on which aggregate, and
> offer to create the factory (`test-data`) or to record the request. **Never** fall back to staging
> data, a fixed id, a user "that already exists", or `SELECT ... LIMIT 1`.

That refusal is the most important point of the skill. Without it, automating at scale produces debt
at scale — generated by AI, which is the worst kind: it arrives faster than the team can review it.

## Step 4 — Write the spec

- **Setup through an API fixture** (`test-data`): the test **creates** the state it needs, with its
  own `runId`, and is independent of order and of previous runs — the six rules in
  `test-data/references/isolation.md`.
- **Forbidden**: fixed waits (`sleep`, `waitForTimeout`, `cy.wait(2000)`) — wait on a **condition**;
  generic assertions (`toBeTruthy`, "status 200" as the only proof, a whole-screen snapshot) —
  assert the **effect of the `then`**; selectors by volatile text or DOM path — use role/`data-testid`.
- **One scenario per spec.** A test that proves three things does not say which one broke.
- **Cleanup by `runId`**, not a `beforeEach` that empties a table (that breaks parallel runs).

`preflight` blocks a PR with a fixed wait or preexisting data (`preflight/scripts/qa-lint.sh`) — here
you avoid it, there the gate confirms it.

## Step 5 — Mutation proof (the test of the test)

Before calling it done: **break the behavior on purpose** and watch the test **fail**. If it passes
with the code broken, it proves nothing — fix the assertion, not the code.
Procedure, and what to do when the mutation survives: `references/mutation-proof.md`.

**No passing mutation proof, no PR.** If it never fails anything, the proof is loose: that is a
symptom, not a success.

## Step 6 — Close the loop

1. Catalog: `status: automated` + `spec: <path>`.
2. **The automation's cost** (`cost`): measure only this slice, from when step 4 started —
   `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cost/scripts/session-cost.py --since=<ISO> --kind=qa` — and
   post the `comment` field it prints on the issue as is (`gh issue comment <n> --body "<comment>"`;
   marker `<!-- ferion:cost kind=qa … -->`). It is QA's cost and is never added to the dev cost.
   Always a new comment — never edit a cost someone else already posted on the issue.
3. A comment on the issue (`issues`) with the scenario id and what is now covered.
4. **Explain in plain language** what the test proves **and what it does not** ("covers the block on
   an outstanding balance; does not cover the message shown on screen — that is L4 and was left out").
5. From here it is the normal flow: `preflight` → PR (`start` takes care of the order).
